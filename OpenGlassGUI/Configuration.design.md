# Configuration design contract

This is the product contract for the configuration editor, color synchronization and presets. Format details belong in [Presets.md](Presets.md). A later explicit product decision must update this contract and its affected consumers together.

## 1. Keep five concepts separate

| Concept | Meaning |
| --- | --- |
| Editing layer | The HKCU or HKLM configuration this window displays and ordinarily edits. |
| Effective configuration | The values selected by runtime precedence across both layers, with automatic/theme/default behavior intact. |
| Windows accent state | The original interactive user's automatic/manual mode and chosen manual RGB, independent of editing layer. Changed write targets have raw before-values. Automatic recovery recomputes derived colors. |
| Saved preset | An explicit, reusable snapshot of effective configuration, optional accent RGB and copied resources. It has no target scope. |
| Preview checkpoint | The before-values for this GUI's net modifications since startup or the last Save. It is not a preset. |

The editor is a layer editor, not a live effective-value inspector. A preset is an effective snapshot, not a dump of the visible controls. Save synchronizes the current Windows accent preference and accepts edits, while New/Update saves a reusable preset. These meanings must not depend on which tab is open.

## 2. Layer display, inheritance and defaults

The default layer is HKLM. `--scope=hkcu` selects the original interactive user's layer, and `--scope=hklm` selects the machine layer. Values are case-insensitive, conflicting duplicates and invalid values are errors, and scope cannot change during a window's lifetime.

Holding Shift while opening **More** reveals **Switch to HKCU/HKLM view**. Switching requires a clean preview and no symbol download, and it never implicitly saves or reverts. It replaces the window in the same process, preserving the original user identity, session editor lock, window placement and selected tab. The new window reads its own layer without changing configuration or Windows accent color. It preserves the transparency command-line mode.

Ordinary controls read and write only that layer. If no valid value exists, display the local default, including existing same-layer active/inactive fallback rules. Never populate ordinary controls with the other layer's values. Accent RGB, Windows transparency and the two color Override deletions have the explicit exceptions in section 6.

| Editing layer | Registry situation | Display and notice |
| --- | --- | --- |
| HKCU | Valid user value, even one numerically equal to a default | Show that local value, with no inheritance notice. |
| HKCU | No valid user value, valid machine value | Show the local default with an inheritance information icon. |
| HKLM | Valid user value takes precedence, whether or not HKLM has a value | Show the machine value/local default with a yellow warning, keeping the control editable. |
| Either | Neither notice applies | Show the local value/default without a layer notice. |

**Default means no customization in this layer.** Explicit Default or reset actions remove that layer's customization according to each control's defined removal behavior, permitting inheritance rather than guaranteeing the renderer's built-in default. Presets share this meaning for ordinary settings. Controls follow specific write or removal behavior, so merely matching a displayed numerical default does not necessarily delete the value. No registry marker suppresses inheritance.

Runtime reads remain independent of the editor:

- Ordinary values: HKCU → HKLM → built-in default.
- Overridable values: HKCU Override → HKLM Override → HKCU base → HKLM base → built-in default.
- Invalid types are unavailable. Continue to the next candidate. Both DWM architectures share this ordering. Machine Override precedence over user base is an intentional compatibility change.

Resource strings accept `REG_SZ` and unexpanded `REG_EXPAND_SZ`, matching runtime reads. Presets capture their text, while checkpoint recovery preserves the original registry type and bytes.

For valid values, this restores the ordering used before commit `d6b4414` (2026-08-02, "Fix override resolution and expand diagnostics"). From that commit through 3.0.2, HKCU base preceded HKLM Override. The affected bases are `ColorizationColor`, `ColorizationAfterglow`, `ColorizationColorBalance`, `ColorizationAfterglowBalance` and `ColorizationBlurBalance`, each with its corresponding `Override` variant. Ordinary settings are unchanged.

Before upgrading, back up the known configuration values in both DWM keys. To retain a user base value's former effect, remove the conflicting machine Override or explicitly set the intended value in the user's Override. The latter is a manual registry option: GUI color choices deliberately remove both color Overrides from both layers. Revert undoes pending GUI changes. After Save, restoring old configuration requires the backup. Reinstalling an older binary changes lookup rules but does not undo saved registry edits.

Base/Override storage is an internal compatibility detail. Ordinary controls and their tooltips do not expose alternate keys, raw source values or dedicated Override-reset controls. Technical registry documentation and explicit transaction reviews can identify exact affected keys without introducing separate editing modes.

## 3. Operation boundaries

All configuration operations target only HKLM and the original interactive user. Never inspect or clean other users' hives.

| Operation | Reads | Configuration writes | Checkpoint / saved content |
| --- | --- | --- | --- |
| Ordinary edit | Selected layer | Selected layer only | Immediate preview. |
| Choose color / Automatic | Selected-layer strength plus original-user color mode/preference | Selected-layer strength parameters, removal of both color Overrides from HKCU and HKLM, original-user mode and direct DWM RGB for Manual, or shell refresh for Automatic, with no explicit AccentColorMenu synchronization (section 6) | Preview of mode/manual RGB and independent raw backups of changed Accent and directly written DWM values. |
| Toggle transparency | Original-user Windows transparency by default, or selected-layer opaque blend with `--no-system-transparency` | Original-user `EnableTransparency` DWORD 0/1 by default, whereas legacy mode edits selected-layer `ColorizationOpaqueBlend`. Win7 also recalculates selected-layer balance Overrides. | Immediate preview with raw recovery. An absent Windows value is restored as DWORD 0, never deleted. |
| Adjust intensity | Selected-layer strength and glass mode | Selected-layer GlassOpacity, and Win7 also writes selected-layer balance Overrides | Immediate preview, with no Windows preference synchronization. |
| Apply preset to HKCU | Saved preset and current values for planning | Covered user values only, preserving HKLM | May replace an existing preview, retaining its first checkpoint. |
| Apply preset to HKLM | Saved preset and both layers for planning | Covered machine values, removing only conflicting valid user values blocking explicit preset values | Same preview behavior, preserving harmless same-value user entries. |
| New / Update preset | Effective configuration, optional original-user RGB, referenced resources | None | Requires a clean preview and publishes saved preset content. |
| Merge into HKLM | Effective known configuration across both layers | Copy effective values first, then remove corresponding valid OpenGlass user values | Requires a clean preview and confirmation, remaining reversible until Save. |
| Merge into HKCU | Effective known configuration across both layers | Establish user values, preserving HKLM | Same clean-preview and confirmation rules. |
| Restore defaults | Known values in selected layer | Remove that layer's known OpenGlass customizations, including internal settings outside the preset surface | May run during another preview, and Revert retains the original checkpoint. |
| Save / Revert | Modification journal | Save synchronizes current original-user RGB to AccentColorMenu without a policy check, then accepts changes. Revert restores journaled registry, color and configuration-resource state | Never changes saved preset content. |

The preset rows describe ordinary configuration planning. Windows transparency uses the original-user mapping, and the independent Windows color operation follows the cross-layer cleanup exception in section 6.

A preset default deletes only its target-layer value in **both** apply directions and does not clear the other layer. Thus explicit values are established for the target user, while default/automatic behavior deliberately remains environment-dependent. Applying a preset is not a guarantee of byte-identical effective results on all machines.

Preset application covers only recognized public settings within that package's catalog version. Merge and Restore defaults cover known OpenGlass settings, including manual-only ones, subject to the two-color-Override exception in section 6: Merge must not copy these retired GUI inputs, while reset may remove them. None of them cleans unknown/future values. The five Windows DWM base values, ColorizationColor, ColorizationAfterglow, ColorizationColorBalance, ColorizationAfterglowBalance and ColorizationBlurBalance, are excluded from configuration cleanup. Color operations separately update the two base RGB values and restore their raw backups as described in section 6, whereas the three base balances are never directly written by the GUI. HKLM merge retains malformed user-source values rather than deleting them, and either target may replace an invalid destination after recording its raw before-value.

The bottom-left **More** menu normally contains **Merge into HKLM/HKCU...** and **Restore defaults...**. Holding Shift while opening it also reveals **Sync** and **Switch to HKCU/HKLM view**, as described in section 2, while Save and Revert remain visible on the right.

**Sync** reloads the current editing layer's controls, inheritance and resource-path notices, the original user's Windows color state, the preset library, transparency/power diagnostics and dwm.exe WER configuration. It preserves the editing scope and does not apply settings, write registry values, request a Windows accent refresh or notify DWM. Sync requires a clean preview: Save or Revert all pending configuration, Windows-color and resource changes first. Both the menu and action entry point check this condition, including pending recovery after a failed operation. Sync never saves or reverts implicitly and does not adopt unrelated external changes into the journal. It is also unavailable during an in-progress preview operation or window shutdown. Library enumeration uses the existing Refresh behavior, including retrying pending library recovery/cleanup, and it does not import, trust or apply packages. Symbol-download progress and user-selected download inputs remain part of the current operation.

A clean preview means no pending GUI net changes, not that Save must have been clicked once. Startup and a successful Revert are clean. Extraction/update/merge must not offer an implicit Save or silently accept edits. Merging differs from applying a preset: merge consolidates the existing effective configuration and may remove same-value user copies when targeting HKLM, whereas preset application preserves harmless copies.

The System tab exposes `EnableUxMitigation` as independent compatibility flags, with built-in default 1. Bit 0 limits Accent override to supported shell windows as detailed in [Accent compatibility](https://github.com/ALTaleX531/OpenGlass/wiki/Configuration-and-registry-reference#accent-compatibility). Disabling the last enabled flag writes an explicit zero instead of deleting the value and restoring default 1. Changing one flag preserves all other bits. The setting follows ordinary selected-layer, live-preview, Save/Revert and inheritance rules, and sends a Backdrop refresh that rebuilds existing Accent effects. It does not enable Accent override or suppress client blur. Applications can independently opt out of Accent override using window properties as described in [Application accent opt-out](https://github.com/ALTaleX531/OpenGlass/wiki/How-OpenGlass-renders-glass#application-accent-opt-out). Preset catalog coverage is defined in [Presets.md#configuration-states](Presets.md#configuration-states).

## 4. One preview transaction model

Every configuration mutation uses the same checkpoint semantics. Record the original raw type, bytes and absence of each modified `(scope, setting)` only once. The Windows color checkpoint separately records automatic/manual mode, manual RGB and changed AccentColorMenu/DWM AccentColor as independent raw values. Missing AutoColorization is interpreted as Manual and restored as an explicit DWORD 0. The two DWM base colors have independent raw backups for Manual recovery, whereas Automatic recovery recomputes current wallpaper RGB instead of restoring old derived colors. Palette/history and other accepted Windows side effects are not raw journal entries. No-op configuration attempts, including resetting an already empty layer, skip DWM notification and preserve any earlier preview. Refresh decisions use changes within the attempt, not session dirtiness. Returning to the baseline or replacing resource contents at the same path still requires refresh. Explicit Windows color operations retain their refresh even when the selected mode or RGB is unchanged. An unchanged Automatic choice stays clean but retains its attempt recovery mode until the whole operation commits, so failure in a later step recomputes the current wallpaper color. Returning a GUI-modified value to its original state removes its net change.

A multi-step attempt gets an operation-before snapshot. Failure restores that attempt, preserving earlier pending edits. Revert restores only net GUI changes, not whole registry directories: first restore the Windows color choice through its mode-specific operation, then restore OpenGlass configuration values/absence, then notify. This order also restores any color Overrides removed by a color choice. Untouched external values survive. An external change to an already modified item does not revoke the GUI's original before-value. Recovery failure stays pending and retryable, and it must never be reported as successful recovery. DWM color/theme notifications are best-effort refresh requests: unavailable windows or failed delivery are logged or skipped, without rolling back successful writes or keeping a restored checkpoint pending. Configuration editing works without OpenGlass loaded, and its next startup reads the saved values. This does not relax registry/file recovery or the Automatic shell request used to calculate the color.

Save explicitly accepts OpenGlass configuration and the selected color mode/manual RGB, then discards the undo baseline, without waiting for Explorer to finish calculating colors or comparing derived registry values. Normal close attempts Revert and stays open if restoration fails. Esc belongs to the focused control, not global Revert. The full preview checkpoint does not survive a process crash. Only an interrupted operation has the recovery described in section 7. Asynchronous Windows writers remain independent, so do not promise isolation from future external writes.

List selection identifies the target of a library operation and does not apply settings. Presets can combine with configuration from either layer, so the GUI does not label or discover a current preset, persist its identity, or compare live settings with library entries. Save/Revert manage configuration changes and retained source notices independently of selection. Status reports only trust or load problems. Removing a library entry does not change configuration.

## 5. A small preset workflow

The local library is a report ListView with Name, Accent color, Author, License and Status columns, small swatches, single/full-row selection, column sorting and adjustable widths. Rows use a 24-DIP image slot with centered 16-DIP color swatches, scaled for the current DPI without enlarging text. Selection survives sorting and refreshes by stable entry ID. Single-click selects, while double-click/Enter or the row context menu applies once. Row menus offer Apply, Update, Export, Delete and Properties. Blank-space menus offer New preset, Import and Refresh. Right-click targets the row under the pointer or clears selection on blank space. Keyboard menus, F5 and Delete follow those operations, while Esc clears selection and never globally reverts. There is no preset button bank or permanent details pane. Merge and Restore defaults are in the bottom-left More menu, while Save/Revert remain at right. Optional extraction fields start collapsed. Import/Refresh appear only in the blank-space menu, and Properties follows Delete in the row menu.

Import review and Properties open on a concise General page, with Changes, Contents and License available as separate tabs rather than displaying all information at once. Descriptions show at most three visible lines, while image previews fill the remaining space and resize with the window. Double-clicking an image displays it at its original size. Batch import uses a list with per-entry details, not expanded reports for every package.

New/Update capture clean effective configuration. Update replaces any selected entry, including imports, without modifying its external ZIP. Export uses saved content. Delete requires confirmation. It actually removes library files but leaves independent current resources and rollback intact. Save, Revert, switching and closing never publish snapshots, and there is no Unsaved draft or Save-a-copy command.

Every external ZIP is validated, previewed with target/differences/color/resources/conversions/ignored fields and accepted through Trust and import. Import does not apply. After confirmation, revalidate the same digest before publication. Admission is local and bound to content, not author identity. Accepted presets apply directly without repeated sensitive-setting or cross-layer confirmation, but permissions, digest and capability checks remain mandatory. Changed or manually added content must be explicitly trusted. No action automatically restarts DWM.

## 6. OpenGlassGUI treats color configuration specially

### Windows transparency

The transparency checkbox defaults to reading and writing `EnableTransparency` under the original interactive user's `SOFTWARE\Microsoft\Windows\CurrentVersion\Themes\Personalize` key, regardless of editing scope or the elevated account. Missing/invalid values display as disabled, matching the shared runtime reader. Equal boolean values are not written. `EnableTransparency` is never deleted. `--no-system-transparency` restores the selected-layer `ColorizationOpaqueBlend` behavior: unchecked writes 1, checked removes that value. The option survives elevation and switching editing scope. The system-mode checkbox has no HKCU/HKLM inheritance icon. Notifications retain the existing best-effort DWM refresh.

Transparency is represented in presets by `ColorizationOpaqueBlend`, and `EnableTransparency` is never serialized. In system mode, capture reads the original user's `EnableTransparency` and inverts its boolean value. Missing or invalid values capture as `ColorizationOpaqueBlend=1` to preserve their disabled effect. Application maps zero or Default to `EnableTransparency=1` and any nonzero value to 0, regardless of editing scope. It leaves both DWM `ColorizationOpaqueBlend` values untouched. The planner and preview/recovery journal record the actual original-user `EnableTransparency` identity and its raw type/bytes/absence, so recovery is independent of the current command-line mode. Revert, failed-attempt rollback and interrupted-operation recovery restore existing raw values exactly, and an absent value is restored as DWORD 0 instead of deleting it. This also applies to recovery records written by earlier versions. `--no-system-transparency` instead captures `ColorizationOpaqueBlend` using ordinary effective precedence and applies it under the ordinary scope rules. Merge and Restore defaults remain DWM configuration maintenance operations and preserve Windows `EnableTransparency`.

### Managed settings and color destinations

The following ten registry names are **OpenGlassGUI managed settings**. This is a GUI policy group, not a new registry value or a change to runtime compatibility.

| Managed settings | GUI rule | Scope |
| --- | --- | --- |
| `ColorizationColor`, `ColorizationAfterglow` | Manual directly updates their RGB while preserving each alpha, and Automatic obtains RGB through the shell refresh. | Always the original interactive user's HKCU, including HKLM editing/application. |
| `ColorizationColorOverride`, `ColorizationAfterglowOverride` | Never capture, create or apply. Color operations always delete both variants in both hives, and only checkpoint recovery may restore deleted values. | Original-user HKCU and HKLM, independent of the editing scope. |
| `ColorizationColorBalance`, `ColorizationAfterglowBalance`, `ColorizationBlurBalance` | Ignore in new preset capture, schema 3 application and ordinary GUI editing. Never directly write or delete. Schema 3 fields are reported ignored and remain in the original digest, while compatibility conversion is specified below. | Neither layer is edited. |
| `ColorizationColorBalanceOverride`, `ColorizationAfterglowBalanceOverride`, `ColorizationBlurBalanceOverride` | The only balance configuration recorded and written by the GUI. Capture resolves explicit Overrides across both hives, and absence means uncustomized. | Ordinary editing targets the selected layer. Preset application and Merge retain their ordinary scope rules. |

Compatibility exception: schema 1/2 import and explicit Merge may convert effective legacy base balances to balance Overrides when no valid explicit Override takes precedence. They write only Overrides to the selected target and preserve all base values. This preserves old appearance settings, but it does not authorize new preset capture to promote Windows-generated balances. The runtime still accepts manually configured base/Override values. Windows API side effects are separate from GUI configuration writes, so the accepted base-balance updates described below remain possible. Color Override cleanup occurs during color selection/preset application, not as unsolicited startup cleanup or during an unrelated edit.

The GUI owns the user's color choice, not every value Windows generates from it. Its color checkpoint records mode/manual RGB and a separate raw Accent value only when that value is changed, while directly written DWM values use independent raw backups. OpenGlass configuration continues to use the ordinary raw-value journal.

| Choice | Original interactive user's Windows operation | Color swatch / preset meaning |
| --- | --- | --- |
| Manual | Set AutoColorization=0, update ColorizationColor/ColorizationAfterglow RGB and DWM AccentColor directly, and send ImmersiveColorSet. | A fixed/custom swatch, or a preset containing accent_color RGB. |
| Automatic | Set AutoColorization=1, synchronously send the forced wallpaper-color request used by shell32 UpdateWallpaperTransition, synchronize DWM AccentColor from the resulting ColorizationColor RGB, then send ImmersiveColorSet. | The multicolor Automatic swatch, or a preset with absent/null accent_color. |

DWM AccentColor belongs to the original interactive user and is Windows state separate from OpenGlass catalog or preset settings, using opaque COLORREF 0xFFBBGGRR. Do not retain the uxtheme RegCreateKeyExW or DwmpSetColorizationParameters IAT hooks or rebuild unrelated companion values afterward. ColorPrevalence writes, palette and history regeneration, Windows base balance changes, and color alpha changes are accepted Windows side effects, with no suppression or individual rollback of those side effects. This acceptance does not authorize unrelated registry cleanup.

Choosing a fixed/custom color **or Automatic must delete ColorizationColorOverride and ColorizationAfterglowOverride from both the original interactive user's HKCU and HKLM, regardless of editing scope**. Even an HKLM editor changes Windows color preference and its generated ColorizationColor/ColorizationAfterglow in that user's HKCU, and an Override in either hive would mask those colors. This is an explicit color-operation exception to layer-only editing, not a general permission to clean the other layer. Each of the four possible deletions is a separate (scope, setting) journal entry with its raw before-value/absence, restored on Revert or failed-attempt rollback. Check access to both layers before changing mode or colors, and do not silently perform only half the cleanup. No other user hive is inspected. There is no explicit-preset exception: new GUI capture/update/application and Merge must not create or copy either color Override. Legacy package entries for them are ignored, even when explicit. Restoring values deleted by this GUI during Revert/failed-attempt recovery is the sole write-back exception, which restores a checkpoint, not a preset setting.

### Intensity and palette

Intensity remains in the selected layer's GlassOpacity in both glass modes. Win7 intensity editing derives that layer's three balance Overrides. The shared calculation saturates the weight curve before unsigned conversion so each balance remains within 0..100 and their sum is 100, including opaque mode at high intensity. Changing intensity does not change automatic/manual mode. Clicking the Automatic swatch obtains native image alpha after the original user's Automatic choice and forced Shell refresh succeed. It derives selected-layer GlassOpacity from that alpha, and Win7 derives all three selected-layer balance Overrides directly from the original byte, without rounding through the slider percentage. Fixed/custom swatches likewise calculate balances from their supplied ARGB. This strength change joins the same preview as the color-mode change, including recovery if native calculation fails. Automatic color refresh/recovery and preset application do not recalculate intensity. Presets retain their own strength settings. In automatic mode, the Custom swatch reads the original user's current accent RGB on color/settings notifications and window reactivation. Coalesce these into a deferred, read-only UI refresh, preserve the last swatch on read failure, and never change registry values, saved presets or preview checkpoints. Alpha is neither new slider storage nor an integrity condition.

Windows 7 Aero shows a **Composition parameters** section immediately below Color intensity, initially collapsed. Its Color balance, Afterglow balance and Blur balance sliders independently edit the selected layer's corresponding Overrides in 0..100, with local defaults 10, 10 and 50 and the ordinary inheritance/precedence notices. Do not populate them from Windows base balances or the other layer. Independent edits do not normalize the other two balances, change intensity or color mode, or clear the other layer. Intensity, transparency and color-swatch operations retain their existing derived-balance calculation and immediately synchronize all three sliders. Preset application, Restore defaults and Revert reload them through the normal settings path. They participate in the same preview transaction as other ordinary settings. Vista hides this section without deleting its values, and switching glass family or refreshing configuration preserves its expansion state. Other advanced manual values remain supported without dedicated controls.

AutoColorization and all color operations target the original interactive user, including HKLM editing and alternate-credential elevation. Swatch selection reflects the actual mode. Include accent color starts checked when that user's AutoColorization is off (missing means off), and invalid types/read failures must be reported. Present RGB in a preset means manual, not merely an optional RGB write, whereas absent/null means automatic, not leave-unchanged. A legacy package follows the mode implied by its converted main RGB. Presets without RGB use the multicolor appearance. The Automatic swatch uses a fixed multicolor gradient background and a fan of five solid-color cards, and its icon remains fixed. Small preset library icons use only the gradient when accent_color is absent/null (including legacy packages with ignored color Overrides), while packages with accent RGB use the color swatch.

Color presets use a single-selection icon ListView with the color name below each swatch. A click invokes a fixed color, Automatic or the existing Custom color, including an already selected item. Double-clicking Custom opens the color dialog, whose new color applies only after confirmation. Focus starts at the selected swatch when entering the palette or initializing a family. Arrow keys and Home/End move a visible focus highlight without applying, and configuration refreshes preserve the keyboard cursor even while the palette is inactive. Enter/Space invokes the focused item. For Custom, either key first applies its existing color when unselected, then opens the editor when already selected. Holding an activation key does not repeat the action. An explicit Custom choice remains selected when its RGB and intensity coincide with a matching built-in color. This is a transient UI preference, cleared by choosing another swatch, switching families, or a configuration refresh that no longer matches. It is not persisted in configuration or preset packages. Selection is synchronized from configuration, independently of focus, and programmatic refresh, blank clicks and canceled dialogs do not apply a color. The selection highlight stays the same when focus moves or the window becomes inactive, while the keyboard focus cue remains separate. The palette wraps at the available width and grows with its rows, using the page's scrolling. Preset-library entries retain their separate report ListView.

### Color preview recovery and Save

All color operations target the original interactive user. Manual writes AutoColorization=0 unconditionally, updates original-user ColorizationColor and ColorizationAfterglow RGB while preserving their individual alphas, and writes DWM AccentColor as an opaque COLORREF (0xFFBBGGRR), skipping equal DWM color values. The two Colorization values must already be readable DWORDs, whereas DWM AccentColor may be absent or have another type, which is backed up before replacement. All preview write targets must be writable before mutation. AccentColorMenu is not a Manual preview target, so preview does not require write access to it.

Automatic selection sets AutoColorization=1, backs up potential shell write targets before the request, and synchronously delivers the verified forced wallpaper-color request used by shell32 UpdateWallpaperTransition with a bounded timeout, allowing sent-message dispatch during the wait for Explorer broadcasts. Consuming an already pending shell result is insufficient after a manual choice. Automatic then reads the resulting ColorizationColor RGB and synchronizes DWM AccentColor as an opaque COLORREF (0xFFBBGGRR), skipping equal values. Shell can update glass RGB while leaving both Accent values unchanged because the uxtheme setter can skip persistence when the shared preference already matches. Do not rewrite ColorizationColor or ColorizationAfterglow directly in Automatic mode. Read AccentColorMenu after the shell request only to reconcile any Shell side effects against the raw backup, removing unchanged journal entries, and do not publish the calculated RGB to AccentColorMenu until Save. Report delivery, read or write failures through the preview recovery path. A timeout does not promise cancellation of work already executing in Explorer, nor does receiver completion prove successful image extraction on every Windows build.

The GUI does not monitor later Explorer RGB/palette writes or add them to a deferred journal, but backs up values involved in its explicit color operation. Do not introduce registry polling, delayed corrective writes, cross-process locks or companion journaling to simulate cross-process isolation. Direct Manual writes are synchronous GUI operations.

Color rollback restores the user's choice rather than a byte-for-byte Windows snapshot:

- Restore the independent raw AccentColorMenu backup first, regardless of active color policy, including for an Automatic baseline, and then reapply the recorded mode and choice.
- Missing AutoColorization means Manual on read. Disabling automatic coloring and restoring Manual always write an explicit DWORD 0, even if the baseline value was absent, and they never delete the value.
- Restore Manual by writing AutoColorization=0 and the checkpoint RGB, then restore ColorizationColor, ColorizationAfterglow, and DWM AccentColor from their independent raw backups to their distinct original values, types or absence, regardless of current policy.
- Restore Automatic by restoring its recorded mode (preserving original nonzero values, while new explicit Automatic selection writes 1) and recomputing a fresh color from the **current** wallpaper via the shell request. Do not reapply old automatic derived colors or old derived AccentColor.
- Revert, window close and failed attempts execute these mode-specific recovery operations alongside the existing OpenGlass configuration transaction. Untouched external values survive Revert. Capability or recovery failures remain explicit, pending and retryable, and they must never be reported as successful recovery.

AccentColorMenu is the persistent Windows preference. Save reads the original interactive user's current ColorizationColor RGB and synchronizes this preference as an opaque COLORREF (0xFFBBGGRR) to AccentColorMenu only if different, skipping equal raw values without a write or rollback entry. It checks write access before publishing. This synchronization occurs regardless of editing scope or active color policy. The write uses the existing preview transaction: raw type, bytes or absence are recorded before mutation, and Save accepts the complete preview checkpoint only after the write succeeds. A failure restores that Save attempt while retaining earlier previews, failed recovery remains retryable, and no extra pending-color state is kept.

### DWM color refresh

The GUI, DWM engine and theme extension share DwmSettings::UpdateType. Backdrop covers the former GUI Colorization category. Theme updates theme resources, Framework updates engine power-state settings, and RestartRequired marks settings that need a restart. All retains the engine's registry-reload meaning of Backdrop | Framework, and it does not include Theme or RestartRequired.

The GUI passes the current DWM notification window and update flags to the shared DwmSettings::NotifyChange helper. Backdrop sends WM_SETTINGCHANGE with wParam=0 and lParam=L"ImmersiveColorSet" through SendMessageTimeoutW with a one-second timeout. SendNotifyMessageW cannot deliver this pointer-bearing message across processes (ERROR_MESSAGE_SYNC_ONLY). This asks native DWM to reload the Accent cache used by modern borders. Theme sends WM_THEMECHANGED with zero parameters through SendNotifyMessageW. Combined flags send backdrop first, then theme, while the other flags send no messages. The GUI does not call private DwmpGetColorizationParameters/DwmpSetColorizationParameters or normalize/persist Windows base balances.

Notify after the operation's writes, including Automatic DWM AccentColor synchronization, or after recorded raw recovery. Both OpenGlass architectures handle WM_SETTINGCHANGE with wParam=0 and the ImmersiveColorSet category by updating the OpenGlass backdrop, then forward the message to the native window procedure. Other WM_SETTINGCHANGE categories are forwarded without an OpenGlass update. WM_DWMCOLORIZATIONCOLORCHANGED retains the OpenGlass backdrop update for compatibility but is not sent by the GUI. Theme-resource changes retain WM_THEMECHANGED and its OpenGlass theme update. These handlers do not drain queued native messages.

Notifications are best effort, not desktop-wide broadcasts or guarantees that rendering has completed. A delivery failure does not undo successful writes or keep completed recovery pending. Registry/file recovery and the forced shell request remain checked operations. Do not infer that native handling must emit a separate WM_DWMCOLORIZATIONCOLORCHANGED for every notification or every setting change.

### GUI system-colour notifications

Upstream wxWidgets 3.3.4 posts `WM_SYSCOLORCHANGE` for each `WM_SETTINGCHANGE` / `ImmersiveColorSet` notification, then updates native themes and propagates system colours to child controls. Because Windows can send notifications before and after a preference change, deferral alone can still observe a stale cached mode. The overlay's `NotifySysColorChange` refreshes uxtheme's cached colour policy via `RefreshImmersiveColorPolicyState` before querying light or dark mode. This keeps wx colours and native controls, including scrollbars, in the active mode. See the upstream [window implementation](https://github.com/wxWidgets/wxWidgets/blob/v3.3.4/src/msw/window.cpp).

MainFrame forwards every native notification to wxWidgets and must not discard a later notification just because a previous update is pending. Only `QueueColorizationRefresh` coalesces read-only swatch updates. It runs after the current operation without writing configuration, touching the preview journal or suppressing native theme processing.

Native theme processing and `WM_THEMECHANGED` stay enabled, and the colour-preset list retains double buffering and deferred updates to its own images and colours after native processing. Hidden pages, collapsed sections and native scrollbars must reflect the current mode when shown. Substituting only a wx mode-query return value is insufficient to verify the real Windows, uxtheme, and native-control transition.

Explicit frame, page and notice colours follow system colour roles through `FollowSystemColours`, which updates them on `wxEVT_SYS_COLOUR_CHANGED`. Parent-matched read-only text backgrounds follow their parent's current colour. Use own colours to prevent children, including the notebook, from inheriting fixed RGB snapshots, while the notebook retains its native themed background. A one-time `SetBackgroundColour(wxSystemSettings::GetColour(...))` freezes the startup colour and must not be used for these surfaces. Preserve native event propagation so hidden pages and their child controls update too.

System-colour handlers update these explicit colours synchronously, and wxWidgets owns the final top-level redraw after propagating the native event. Do not recursively refresh every surface again. Deferred custom-image rebuilds own their subsequent repaint: the colour-preset list repaints once after updating its colours and images, and the preset-library list replaces only its thumbnails on theme/DPI changes instead of clearing and reinserting rows. Theme/DPI image updates must preserve row order, image-to-row mapping, selection, keyboard focus and scroll position without replaying sorting or selection. Native DPI layout may change row height and the amount of visible content, but it must not reset navigation to the first row.

### Native Automatic alpha and later wallpapers

The GUI and theme extension share the `IDesktopWallpaperPrivate` declaration in `Common/DesktopWallpaper.hpp`. Only an explicit GUI Automatic-swatch action calls `ComputeImageColorizationColor` for strength, and its RGB is not applied. Windows RGB still comes from the completed forced Shell request. The call follows enabling Automatic because, in the inspected shell32 10.0.17763.737 and 10.0.26100.9549 implementations, the native method checks `CAutoColorization::s_AutoColorEnabled` before updating its cached image color. Do not calculate while Manual and treat that cached result as a fresh wallpaper calculation.

The GUI uses the existing original-user token scope, local-server COM activation with [CLSCTX_ENABLE_CLOAKING](https://learn.microsoft.com/en-us/windows/win32/api/wtypesbase/ne-wtypesbase-clsctx), and [dynamic proxy cloaking](https://learn.microsoft.com/en-us/windows/win32/com/cloaking) for the method call. Alternate administrator credentials must not select the administrator's wallpaper. A failed COM call follows ordinary failed-attempt recovery, and the GUI adds no fixed-alpha or registry-alpha fallback. The strength values participate in ordinary layer-scoped Save/Revert, with no extra alpha key or preset field.

**Native strength calculation:** both inspected revisions initialize `CAutoColorization::s_uAlphaLow` to 125 (`0x7D`) and `s_uAlphaHigh` to 175 (`0xAF`). Successful image-color selection uses:

```text
rangeSum = sum(max(R, G, B) - min(R, G, B))
alpha = min(175, 125 + floor(rangeSum / pixelCount))
```

`CAutoColorImageData::CreateImageColorizationData` caps each analysis dimension at 256 pixels. The sum includes pixels with nonzero image alpha, where `pixelCount` is the full analysis width times height, including skipped transparent pixels. Multiple images contribute their sums and pixel counts before division. The legacy path unpremultiplies RGB first, whereas 26100's feature-41486951 weighted-RGB path skips that step but retains the alpha formula. This alpha represents colorization strength derived from RGB statistics, rather than the image file's transparency.

The normal calculated range is therefore **125..175**, reaching 175 whenever the average channel difference is at least 50. Different wallpapers can reach the same ceiling. These bounds do not describe every COM result: native color-selection fallback can retain `0xC4FFFFFF` (alpha 196), and initialization can reuse `HKCU\Control Panel\Desktop\ImageColor`. OpenGlass continues consuming the returned alpha without adding a clamp or substituting a constant. These observations apply to the two inspected revisions, not a guaranteed API range for every Windows build.

Percentage conversion is a separate source of rounding: the shared helpers map `175 -> 69% -> 176`. GUI Automatic balances use the original COM byte directly, and only `GlassOpacity` is rounded. The extension getter likewise retains the stored byte when it already represents the effective percentage, and otherwise reconstructs it from `GlassOpacity`. A later registry/tool value of 176 does not establish a fixed native alpha of 176, nor identify which writer performed the conversion.

**Known Shell alpha loss:** in shell32 10.0.26100.9549, `CDesktopBrowser::_SetDWMAndImmersiveColor` converts its ARGB input to COLORREF using only the RGB bytes before calling `SetUserColorPreference` and `SetDwmColorizationColor`. The original alpha is lost at that boundary, independently of the optional luminance cap. The final registry `ColorizationColor` alpha therefore cannot substitute for the native image-calculation result.

Later wallpaper changes can take that same Shell path without either GUI or themecpl participation. OpenGlass retains the last explicitly written `GlassOpacity` and balance Overrides while Windows updates the RGB. This is not continuous native-alpha adaptation. A community modification could address the Shell path separately, but OpenGlass neither depends on such a modification nor adds a watcher, hook or corrective write to reproduce it. Fixing only Windows base alpha/balances would still leave existing OpenGlass Overrides in precedence, so a future integration must define how to update effective strength.

### Color-selection policies

PersonalColors_Background selects the forced-color policy path, not just a write restriction. When that policy is active with valid colors, GetGroupPolicyColors supplies the background/accent pair from PersonalColors_Background and PersonalColors_Accent instead of the user StartColorMenu/AccentColorMenu pair. NoChangingStartMenuBackground gates implicit preference refresh without itself supplying a replacement color. The [Windows policy documentation](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-controlpaneldisplay#cpl_personalization_personalcolors) describes forced background/accent colors. Mere presence of a malformed registry value does not establish a valid policy color.

Skipping AccentColorMenu during preview does not stop Windows color propagation: a later system refresh may propagate the policy colors to DWM. Manual writes the requested OpenGlass DWM RGB and does not change or copy policy values, so its write cannot guarantee persistence against later policy-driven writes. Automatic and Automatic recovery delegate to the shell, whose resulting color remains subject to policy and need not come from the wallpaper.

OpenGlassGUI does not consult color-selection policies when synchronizing AccentColorMenu at Save time (see [Color preview recovery and Save](#color-preview-recovery-and-save)), and policies themselves are never modified. Save synchronizes AccentColorMenu unconditionally with respect to policy, and Windows remains responsible for applying policy colors.

NoChangingStartMenuBackground gates the normal cache/registry refresh branch used by GetImmersiveUserColorSetPreference, but it does not prohibit explicit setters. The logon path can read the preference and invoke a setter separately. Save therefore publishes the current preference even when this flag is nonzero. Until Save, Windows can still consume the previous AccentColorMenu and overwrite preview RGB, as direct DWM writes do not prevent later external or policy-driven updates.

In the inspected uxtheme 14393.0 and 26100.9549 implementations, an eligible registry reload through this getter can call `CImmersiveColorImpl::SetColorPreferenceHelper(&preference, notify, false)`, rather than the exported `SetUserColorPreference`. The last argument selects `_UpdateColorPreferenceForDWM` instead of the full preference-registry write path. The helper broadcasts `WM_SETTINGCHANGE / ImmersiveColorSet` only when notifications are requested and its success conditions are met. Not every getter call broadcasts: the path has initialization, identity and preference checks, while 26100.9549 also suppresses this notification in AppContainer and can call the helper with notification disabled for an unchanged preference.

Once the process has cached a nonzero `REG_DWORD` from `HKLM\SOFTWARE\Policies\Microsoft\Windows\Personalization\NoChangingStartMenuBackground`, it skips that getter branch. This prevents broadcasts originating from that branch and can reduce repeated GUI color-control refreshes and associated stutter. It does not stop registry watching, explicit setters or other notification sources. In both inspected versions, `RefreshImmersiveColorPolicyState` updates this cached flag only after a successful DWORD read. Deleting the value or supplying the wrong type leaves the previous flag in place even after a reread. A successfully changed flag can itself trigger the same broadcast when color data is initialized. OpenGlassGUI does not modify this policy, and these findings do not establish identical behavior on every Windows version.

wxWidgets theme notifications refresh this GUI process's cache (see [GUI system-colour notifications](#gui-system-colour-notifications)). Mid-session forced-color changes may leave other process caches out of sync, and RGB persistence is not guaranteed.

### Why Manual does not use SetUserColorPreference

The observed implementation of SetUserColorPreference has a serious cross-process consistency defect: it publishes palette/history changes before completing the persistent preference, writes StartColorMenu and AccentColorMenu separately, and allows a registry-watcher read to publish an obsolete preference back to shared memory and DWM. An atomic shared-memory exchange does not make this multi-step operation atomic. This is a race condition in the cross-process read/modify/write protocol, not a GUI selection or rendering failure.

On the examined Windows 10.0.26100.9549 binaries, ProcMon captured both failure modes: consumers read new StartColorMenu with old AccentColorMenu between the GUI's writes, and another consumer read a complete old preference, then wrote the old DWM RGB after the GUI had successfully written the new RGB. Its stack ran from a Windows.UI.Immersive registry-watcher callback through GetImmersiveUserColorSetPreference, SetColorPreferenceHelper, _UpdateColorPreferenceForDWM and DwmpSetColorizationParameters. Even the consumer's DWM Get read the new color before its stale request replaced that RGB. Thus successful registry writes and API return values do not establish a consistent final color. The helper's same-preference optimization can also skip subsequent DWM synchronization. Forcing a broadcast does not force that write. This is an observed API design flaw, not a claim about Microsoft's intent or every Windows revision.

To avoid this race and publishing the persistent preference on every preview edit, OpenGlassGUI avoids SetUserColorPreference, SetImmersiveColorPreferenceInSharedMemory, uxtheme RegCreateKeyExW/DwmpSetColorizationParameters IAT hooks, companion journaling, or regenerating AccentPalette/StartColorMenu/history. Direct DWM writes and targeted ImmersiveColorSet notifications do not depend on watcher propagation, and forced manual broadcasts are prohibited. Save synchronizes AccentColorMenu to record the matching source for later Windows refreshes, but cannot serialize external processes.

### Known limits

Automatic selection and recovery require the original user's Explorer. Leaving Automatic also checks that recovery capability before mutation, and if Explorer is unavailable, even a Manual selection can fail preparation. A missing DWM notification receiver alone does not prevent configuration editing or completed recovery.

This is not a cross-process transaction or a guarantee against arbitrary late writers. Manual persistence is written synchronously, but a successful registry write does not prove that DWM has rendered it. Later external writers remain independent. The GUI does not regenerate Start color, palette or history, promise that all Windows surfaces adopt the same RGB, or protect alpha against subsequent Windows writes, and its direct ColorizationColor/ColorizationAfterglow writes preserve their individual alpha. No polling, delay/retry loop, cross-process lock or hook is added.

This design does not patch system DLLs, install COM hijacks or add Host RGB monitoring. The separately discussed uxtheme patcher is a different project, not a dependency of GUI color selection.

## 7. Format, resources and simplicity

Interrupted-operation records persist raw numeric setting IDs alongside setting names. Append new settings to `Settings::Id` and its catalog, and keep existing IDs stable so older recovery records remain readable.

Package archive specifications, schema versions and catalog conversions are defined in [Presets.md#archive-format](Presets.md#archive-format) and [Presets.md#configuration-states](Presets.md#configuration-states). Library storage, admission records, deployment staging and configuration resource paths are defined in [Presets.md#library-admission-and-resources](Presets.md#library-admission-and-resources). Author metadata, source notices and the attribution grant are specified in [Presets.md#author-and-attached-terms](Presets.md#author-and-attached-terms) and [Presets.md#rights-envelope](Presets.md#rights-envelope).

Snapshots retain legal automatic/theme sentinels and defaults rather than baking them into temporary output values. Unknown or out-of-catalog settings participate in the original digest but are not written or used to clean configuration. Runtime support, preset surface/catalog version and GUI controls are separate responsibilities.

Resource bytes/absence and source notices join the preview journal, including same-path changes, operation rollback and first-baseline Revert. Send a Theme refresh for changed contents even when the registry path is identical. Notification delivery does not prove compositor completion.

Prefer a clear rule and a disclosed limitation to a new state machine for a speculative edge case. Simplification must not remove transactional restoration, identity checks, source notices or hostile-input validation. Do not turn resource provenance into the editor's organizing principle or repeatedly increment an unpublished schema during exploration.

## 8. Privileges and installation

The installer's optional completion-page launch uses runasoriginaluser, so the GUI starts under the installing interactive user's pre-UAC identity and performs its own authenticated elevation. Do not use runascurrentuser here: alternate administrator credentials would otherwise become the GUI's configuration user. If Setup was explicitly started already elevated, Inno Setup cannot recover a pre-elevation identity, so launch the GUI from the intended user's desktop or Start menu instead.

The GUI elevates at startup with an `asInvoker` manifest and an authenticated original-user handoff through an ACL-protected random named pipe. It validates both process directions, image, session ID, PID, and server-token SID before trusting the original user identity, preventing alternate administrator credentials from substituting the administrator's configuration. Running one editor per interactive session prevents competing color previews. Scope is independent of privilege: System tab configuration follows scope, while services, symbol downloads, and WER retain administrative targets. Symbol downloads, WER mutations, and HKLM merge each disable their controls when unelevated and require an elevated token at action entry. Read-only Diagnostics remains available. Library storage is protected. The GUI does not support or promise on-demand elevation during unelevated HKCU use.

Uninstall policy is independent of editor scope. See [installation boundaries](../Scripts/README.md#installation-boundaries) for cleanup choices, account ownership, and protected runtime directories.

WER mutations are immediate HKLM operations performed outside Save and Revert. They apply strictly to `LocalDumps\dwm.exe` rather than global crash collection. Enabling creates the destination folder before writing `DumpType=2`, `DumpCount=1`, and an explicit `REG_EXPAND_SZ` path. Disabling removes only the per-application key. The installer owns the protected default dump directory, and disabling collection or uninstalling must not delete a user-selected custom dump folder.

The elevated GUI accepts preset ZIP drops from unelevated Explorer by allowing only `WM_DROPFILES`, `WM_COPYDATA`, and the shell message `0x0049` through the main window's UIPI filter. Keep this filter exception window-local, and route every dropped file through the same strict validation used by **Import...**.
